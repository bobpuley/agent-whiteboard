## 1. 1.0 Release Readiness & npx Distribution (F27–F28, NF33–NF37 in `03`)

- **Production entrypoint (`bin/cli.js`):** new `bin/` script, referenced by `package.json`'s `bin` field (`"agent-whiteboard": "bin/cli.js"`), with a `#!/usr/bin/env node` shebang. It imports and runs the compiled `dist/server/index.js` (today's `server/index.ts` entry, already dependency-only — no dev tooling in its own import graph), then opens the browser via the existing `open` dependency. This is the thing `npx agent-whiteboard` actually executes; it must never `require`/`import` `tsx`, `vite`, `concurrently`, or `wait-on`.
- **Static file serving (`server/app.ts`):** `createApp()` gains a static-file middleware (`@hono/node-server/serve-static` or equivalent) that serves `dist/client` when running in production mode, so the compiled server is self-sufficient without the Vite dev server. Dev mode (`npm run dev`) is unaffected — it keeps using Vite's dev server + proxy, as today. Mode selection: presence of `dist/client/index.html` relative to the running entrypoint, or an explicit `NODE_ENV`/flag check — exact mechanism to be settled during implementation, not a product-level decision.
- **Loopback guardrail (F27):** at startup in `server/index.ts`, before `serve()` is called, validate `HOST` against a loopback allowlist (`localhost`, `127.0.0.1`, `::1`). If it doesn't match and no explicit opt-in env var (e.g. `ALLOW_NON_LOOPBACK=1`) is set, fail fast with a clear error instead of binding. This replaces "HOST defaults to localhost" (a soft convention) with an enforced guarantee, matching the accepted single-user/local-only trust model in `02`.
- **Accessibility fix (F28):** `NodeActionPopup.svelte` gains a `keydown` handler — reuse the existing `trapFocus` action's `Escape`-to-close behavior (`client/src/lib/trapFocus.ts`) rather than a bespoke handler, and extend `popup-item`'s handler to also fire on `" "` (Space), matching native `<button>` semantics. No new dependency.
- **Package/publish shape (NF33–NF36):** `package.json` gains `license: "MIT"` (this milestone's shipped value — superseded `1.0.1` onward by a deliberate switch to `PolyForm-Noncommercial-1.0.0`, see `CHANGELOG.md`'s `1.0.1` entry; `1.0.0` itself remains MIT since that grant isn't retroactively revocable), `description`, `repository`/`homepage`/`bugs` pointing at `github.com/bobpuley/agent-whiteboard`, `author`, `keywords`, and a `files: ["bin", "dist", "README.md", "LICENSE", "CHANGELOG.md"]` allowlist; `private: true` is removed; `version` becomes `1.0.0`. The `build` script (already `tsc -p tsconfig.json && ... && vite build`) is the one producing everything `files` references — no new build step, just ensuring `bin/cli.js` is either plain JS (no compile step needed) or included in the `tsc` project's output.
- **CI (NF37):** new `.github/workflows/ci.yml` running on `push`/`pull_request` to `master`: `npm ci`, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. No deploy/publish automation in this milestone — publishing stays a manual, deliberate step per the project's existing sprint-close protocol (`CLAUDE.md` rule 7).
- No MCP tool contract changes, no snapshot/persistence format changes — this milestone is packaging/runtime/CI/one a11y fix only, isolated from the render pipeline.

## 3. Vega-Lite CSP `unsafe-eval` Fix (F31 in `03`)

- **`server/app.ts`'s `CSP_HEADER`:** `script-src` gains `'unsafe-eval'` (`'self' 'unsafe-inline' 'unsafe-eval'`), so Vega/Vega-Lite's client-side expression compiler (`new Function(...)`, used by `vega-embed` for scales/signals/interactive encodings) is permitted to run. This is the one CSP the live browser render path (`POST /render` → `App.svelte` → `VegaLite.svelte`) is actually served under.
- **`server/export-html.ts`'s two CSP strings (`cdn`/`offline` export modes) are explicitly left unchanged.** Vega-Lite in an exported HTML file is pre-rendered to static SVG server-side at export time (`vl.compile(spec).spec` → `vega.parse()` → `new vega.View().toSVG()`) — no client-side expression compilation happens when the exported file is opened, so there is no eval need to grant there. Widening that CSP too would be an unjustified capability increase for a self-contained offline artifact; if a future renderer needs client-side eval inside an export, that's a separate, deliberate decision.
- No other module touched — no new dependency, no data-flow change, no MCP/REST contract change.

## 4. Design Debt — Client Hardening (F32–F33, NF38–NF44 in `03`)

- **WS reconnect (F32):** `client/src/ws.ts`'s `connectWebSocket()` gains bounded exponential-backoff retry logic inside its `close` handler (a thin wrapper around the existing single-socket setup, not a new abstraction). On successful reopen, it re-dispatches `ws:connected`; no client-side state replay is added since the server already treats reconnecting clients as stateless (its next `replace`/`clear` command repopulates everything). `App.svelte`'s disconnect banner copy changes from "restart `npm run dev`" to reflect the retry-in-progress state, only falling back to the manual-restart message after the retry budget is exhausted.
- **Theme tokens (F33):** no new tokens — `Mermaid.svelte`, `Katex.svelte`, `VegaLite.svelte`, and `NodeActionPopup.svelte` swap their hardcoded hex values for the existing `--board-danger`, `--board-danger-bg`, `--board-text`, `--board-bg`, `--board-border-mid` custom properties already defined in `theme.css` and used by the app's chrome.
- **Mermaid DOMPurify (NF38):** one additional `DOMPurify.sanitize()` call in `Mermaid.svelte`, immediately after `mermaid.render()` resolves and before the existing `token !== renderToken` staleness check — same call shape `Html.svelte` already uses. No new dependency (`dompurify` is already in `client`'s dependency tree).
- **Typed snapshot responses (NF39):** a small shared `ApiResult`-shaped interface (`{ ok: boolean; error?: string }`) added to `client/src/lib/snapshotTypes.ts` (or co-located in `snapshotActions.ts` if that file doesn't already exist), cast against each of `snapshotActions.ts`'s three `res.json()` calls — no new validation library, matching `fetchSnapshots.ts`'s existing convention.
- **Non-null-assertion removal (NF40):** `RendererEntry.props` in `registry.ts` is retyped to take a context whose `presentation` field is non-nullable; `App.svelte`'s single call site performs the null check (already implicit in its `currentComponentType === rendererKey` guard) when constructing that narrowed context object, so the invariant moves from a caller-side comment into the type signature. No other renderer call site exists today, so this is a local, non-breaking retype.
- **`scopeCss` parity test (NF41):** a new unit test (client or server suite — either is fine, since the test just imports both) asserts `client/src/lib/scopeCss.ts` and `server/export-html.ts`'s `scopeCss()` produce byte-identical output for a shared fixture set. No production code changes; this is a regression net, not a dedup — the longer-term shared-module option from the Design Debt Log stays deferred.
- **New unit tests (NF42):** `trapFocus.test.ts` added under the same `tests/unit/client/` convention as every other tested module, covering the behaviors listed in `03`. `download.ts`/client `scopeCss.ts` get minimal smoke-level tests in the same pass — lower priority, bundled here only because they're cheap once the test harness pattern is set up for `trapFocus`.
- **`Icon.svelte` extraction (NF43):** a new `client/src/lib/Icon.svelte` (or `icons.ts` path-data module + one generic component) replaces `App.svelte`'s five-plus inline `<svg>` blocks. Pure refactor — no visual or behavioral change, no new dependency.
- **Mermaid id fix (NF44):** one-line change in `Mermaid.svelte` — `` `mermaid-${token}` `` (the existing `renderToken` counter, already unique per render) instead of `` `mermaid-${Date.now()}` ``.
- All 9 items are entirely `client/src/**` changes — no MCP tool contract changes, no snapshot/persistence format changes, no server-side behavior changes.

## 5. Design Debt — Data Integrity & Export Isolation (NF45–NF47 in `03`)

- **`nodeToFrame` validation (NF45):** both unchecked-cast sites (`server/app.ts`'s snapshot-load route, `server/snapshot-reader.ts`'s `findSnapshotByIdInWorkspace`) are replaced with `nodeToFrameSchema.safeParse(...)`, reusing the canonical schema already exported from `server/validate.ts`. A failed parse drops the field rather than throwing, consistent with existing malformed-`frames` handling.
- **Export pipeline isolation (NF46):** the exact mechanism (worker-thread rendering vs. passing explicit `window`/`document` instances to DOMPurify/mermaid, if those libraries support it) is an implementation decision, not a product one — to be settled during implementation. Either way, the existing `exportQueue` promise-serialization can be removed or kept as a secondary safety net once true isolation exists; no MCP/REST contract change either way.
- **Dev-port config (NF47):** `client/vite.config.ts` reads `process.env.CLIENT_PORT`/`process.env.PORT` (with today's `5173`/`3000` as defaults) instead of hardcoding them, for both `server.port` and the proxy target URLs. Dev-only change — no effect on the production `npx agent-whiteboard` path, which is already single-port.
- No snapshot/persistence file format changes, no MCP tool contract changes.

## 6. Design Debt — Server Hardening & Performance (NF48–NF49 in `03`)

- **Body size limit (NF48):** Hono's `bodyLimit` middleware (`hono/body-limit`) applied globally in `createApp()`, ahead of route-specific handlers, with a single configurable cap (5–10 MB). Returns the framework's standard 413 on overflow — no custom error-handling path needed.
- **Async fs I/O (NF49):** `viewport-cache.ts`, `snapshot-reader.ts`, `snapshot-writer.ts` swap `fs`'s sync functions for `fs/promises` equivalents on the loop-heavy paths (`listSnapshots`, `listAllSnapshots`, delete operations); call sites become `async`/`await` up their existing call chains (already async at the Hono route-handler level, so no new sync/async boundary is introduced upward). The viewport cache additionally moves from "read-modify-write the whole file every call" to a debounced write or an in-memory cache flushed on an interval — exact strategy is an implementation decision. (A flush-on-shutdown variant was considered and dropped from scope: no entrypoint in this codebase installs a `SIGINT`/`SIGTERM` handler today, so that variant would require adding graceful-shutdown infrastructure as a prerequisite — out of scope for this milestone unless a future finding motivates it.)
- No MCP/REST contract changes — these are internal I/O-strategy changes behind existing function signatures.

## 7. Design Debt — Server Hygiene & Tooling (NF50–NF54 in `03`)

- **Explicit crypto import (NF50):** `server/snapshot-writer.ts` adds `import { randomUUID } from "node:crypto";` and calls `randomUUID()` directly, removing the bare-global dependency.
- **Typed channel notification (NF51):** `server/channel.ts` defines a minimal local interface (e.g. `interface NotifiableServer { notification(params: {...}): Promise<void>; }`) and casts the MCP `Server` instance to that instead of `any`; the existing `.catch(() => {})` is replaced with `.catch((err) => console.error(...))` (or equivalent) so failures are visible.
- **Port validation (NF52):** a small shared helper (e.g. `parsePort(value: string | undefined, fallback: number): number`) used by `server/index.ts` (`PORT`) and `server/channel.ts`/`server/app.ts` (`CHANNEL_PORT`), throwing a clear error before `serve()`/`.listen()`/`fetch()` is attempted with an invalid value.
- **`app.ts` route split (NF53):** route registrations move into `server/routes/{render,slideshow,snapshots,export}.ts`, each exporting a `(app: Hono) => void` registration function invoked from `createApp()`. Shared logic already lives in `render-core.ts`/`persist.ts`/`validate.ts` and is unaffected — this is purely moving route-declaration code, not shared logic.
- **vite/vitest upgrade (NF54):** dependency-version bump only; `@sveltejs/vite-plugin-svelte`'s version constraint is checked against the new `vite` major before upgrading, and `client/vite.config.ts`'s proxy setup (including the WS proxy) is re-verified post-upgrade since dev-server behavior is the most likely regression surface.
- No MCP/REST contract changes, no snapshot/persistence format changes — this entire milestone is internal hardening/maintainability with no user-visible behavior change.

## 8. Workspace Export/Import for Sharing (F34–F40, NF55 in `03`)

- **Delete confirm text (F34):** `DeleteExportModal.svelte`'s whole-workspace confirm button interpolates `selectedWorkspace.name` into its "Click again to..." label instead of the current static string — a one-line template change, no new state.
- **Export format toggle (F35):** a new `exportFormat: "html" | "zip"` local variable in `DeleteExportModal.svelte`, defaulting to `"html"`, driving a small segmented-control UI in step 2. `runWholeAction()`/`runSelectedAction()` branch on it to call either the existing `exportItems()` (HTML) or a new `exportZip()` (client `lib/snapshotActions.ts` or a new `lib/zipActions.ts`) with the same `{workspace, id}[]` item shape already used today.
- **Zip export pipeline (F36):** a new `server/export-zip.ts` (`generateExportZip(items, workspace): Promise<{zip: Buffer, downloadFilename: string}>`), registered as `POST /export-zip` in `server/routes/export.ts` alongside the existing `GET /export`/`POST /export-html`. Unlike HTML export, this needs no rendering/sanitization pass — it reads each item's raw snapshot JSON file via `snapshot-reader.ts` (a new `findSnapshotFileById`-style lookup returning the raw file path, not a rendered record) and adds it byte-for-byte to the archive, plus one generated `manifest.json`:
  ```json
  { "formatVersion": 1, "workspace": "<name>", "exportedAt": "<ISO-8601>", "appVersion": "<package.json version>", "snapshots": ["<filename>", ...] }
  ```
  All items in one export request must share the same `workspace` (the manifest format is single-workspace) — rejected with a 400 if not, a constraint the existing `DeleteExportModal` UI already satisfies today (it only ever exports from one `selectedWorkspace`) but that `POST /export-zip`'s contract enforces explicitly rather than assuming. New server dependency: **`archiver`** (streaming zip creation, in `dependencies` since `server/export-zip.ts` ships in `dist/server`).
- **Import UI (F37):** a new `client/src/ImportModal.svelte` (not a mode of `DeleteExportModal` — the interaction shape is different: pick a file, not pick a workspace/snapshots) triggered by a new toolbar button, plus a drop-zone handler on the same component/overlay for drag-and-drop. On file selection, the client reads just `manifest.json` out of the zip locally (new client dependency: **`jszip`**, in `dependencies` per this repo's existing convention of listing client-bundled runtime libraries there) to learn the workspace name *before* uploading anything — this lets the collision prompt (F38) render immediately using the `workspaces` list the app already has in memory, with no server round-trip needed just to check for a name collision.
- **Collision prompt (F38):** if the manifest's `workspace` name matches an existing entry in the already-loaded workspace list, `ImportModal.svelte` shows the merge/rename/cancel choice inline (same visual language as `DeleteExportModal`'s confirm step); "rename" pre-fills a text input with the first `"<name> (n)"` that does't collide. Once resolved, the client `POST`s `multipart/form-data` to a new `POST /import` (`server/routes/import.ts`, `registerImportRoutes`) with fields `file` (the zip), `targetWorkspace` (resolved name), and `mode` (`"merge"` if the name already existed and the user chose merge, else `"create"`).
- **Import pipeline (F39, NF55):** `server/import-zip.ts` extracts the upload to a fresh temp directory first (never directly into the live snapshots tree) using **`extract-zip`** (in `dependencies`; chosen because it validates every entry's resolved path stays inside the target directory before writing, closing the zip-slip risk noted in `02` as a property of the library itself rather than hand-rolled path math). After extraction: `manifest.json` is parsed and schema-validated (reject with a clear error if missing/malformed — never trust the client's earlier read of it), `targetWorkspace` is re-validated with the existing `validateWorkspaceInput()`, and:
  - `mode: "create"` — the destination directory must not already exist (re-checked server-side, defense in depth against a stale client-side collision check); every manifest-listed file is moved in as-is.
  - `mode: "merge"` — the destination directory must already exist; each incoming file is compared against the destination's existing files by the snapshot `id` embedded in its JSON (reusing the existing per-file read already done by `snapshot-reader.ts`'s helpers): no match → moved in as a new file; same `id` + same `timestamp` → skipped; same `id` + different `timestamp` → the older of the two files is deleted and the newer one moved in (guaranteeing at most one file per `id`, per `02`'s pre-existing-footgun note). `id`-less legacy snapshots are always treated as "no match."
  - The 50MB cap (NF55) is enforced via Hono's `bodyLimit` on this route specifically (higher than the global 10MB JSON cap — `hono/body-limit` supports a per-route override), checked before the upload is even buffered.
  - The temp directory is removed in a `finally` regardless of outcome.
  - Returns `{ ok: true, workspace, added: number, updated: number, skipped: number }`.
- **Post-import focus (F40):** on a successful `POST /import` response, the client picks the newest snapshot (by `timestamp`) among the ones reported `added`/`updated` for that workspace and calls the existing `POST /snapshots/load` with it — reusing the current render/broadcast pipeline instead of inventing a new "switch active workspace" concept, since loading a snapshot already has that as a side effect (`render-core.ts`'s `setLastWorkspace()` calls). The modal then shows the `{added, updated, skipped}` counts as its done-summary instead of a bare success line.
- No MCP tool changes — this feature is scoped to the browser UI (human-to-human workspace sharing), not agent-facing; a binary zip upload doesn't fit MCP's JSON tool-call contract well and there's no demonstrated agent use case for it yet.
- Snapshot/persistence *file format* is unchanged — export/import operate on the existing `SnapshotFile` JSON shape verbatim; only the transport (zip instead of individual REST calls) and the new `manifest.json` are new.
